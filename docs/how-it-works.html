accord-cron-lab · how the pieces fit

Accord Cron Map

A walk through the whole system: who starts a job, what runs, where the result is stored, and how the dashboard decides whether something is wrong.

The server crontab calls a URL. The API runs that job, writes down what happened in Mongo, and the dashboard reads those notes.

The big picture

One crontab call, end to end

1 crontab calls the URL · 2 the route hands the job to the tracker · 3 the tracker calls the job function · 4 the job downloads the Accord file · 5 it writes the rows to the feed collection · 6 the tracker records the run in cron_runs and cron_jobs. The dashboard only ever reads.

Follow one call

What happens when the crontab fires at 10:01

The crontab line on the server looks like this:

1 10 * * *  curl -s -H "x-cron-secret: $CRON_SECRET" http://127.0.0.1:4000/api/accord-cron/current_nav

  1. The route checks the secret and finds the job

    routes.js

    Wrong secret: 401. Unknown job key: 404. Otherwise it starts the job and answers 202 Accepted at once, so curl never waits on a long job.

  2. The tracker works out which schedule time this call belongs to

    CronTracker.js → schedule.js prevSlot()

    The call arrived at 10:01:03, so it belongs to the 10:01 slot. That goes into the run as scheduledFor.

  3. Is the job switched off?

    If enabled is false, it saves a skipped run with the reason "job is disabled" and stops.

  4. Take the lock

    takeLock()

    One atomic update on the job document: "set the lock to me, but only if it is empty or expired". If another process holds it, this call saves a skipped run ("already running") and stops. Two calls can never run the same job at once.

  5. Save a "running" record

    A new document in cron_runs with status running. From now on the dashboard can see it.

  6. Run the job, keep the lock alive

    startHeartbeat() + the job function

    While the job works, a timer pushes the lock's expiry 2 minutes forward every 30 seconds. The job returns { fetched, processed } or throws.

  7. Decide the result

    Threw an error → failed. Accord gave 0 rows → warning. Otherwise → success.

  8. Save the result and release the lock

    saveResult()

    Updates the run in cron_runs. Updates the job in cron_jobs: lastRun, lastSuccessAt, and consecutiveFailures (reset on success, +1 on failure). Then clears the lock if it is still ours.

Inside a job

What an Accord job does

Most jobs are made by defineAccordJob(). You give it a few settings and it returns the function the tracker calls.

const currentNav = defineAccordJob({
  file: 'Currentnav',          // which Accord file
  section: 'MFNav',            // which Accord section
  dump: m.CurrentNavDump,      // staging collection
  target: m.CurrentNav,        // real collection
  mergeOn: 'schemecode',       // key used to match rows
  project: { schemecode: 1, navdate: ..., navrs: 1, prevnav: 1 },
});

  1. Download

    GET Accord's /RawData/GetTxtFile with today's India date as DDMMYYYY. Times out after 60 s. Any HTTP or network error becomes one readable message, such as Accord Currentnav: HTTP 500.

  2. Stage

    Insert every row into the dump collection, tagged with this run's runId.

  3. Merge

    A Mongo $merge copies only this run's rows into the real collection: replace if the key exists, insert if not. Each row gets cronRunId and crondate.

  4. Count

    Count rows in the real collection with this cronRunId. That number is processed.

  5. Clean up

    Delete this run's staging rows, even when an earlier step failed. If the process crashes first, a 24-hour TTL index removes them.

A job that does not fit this pattern (like navSanityCheck) is just a normal async function that returns { fetched, processed } and throws on failure.

The lock

Why the lock expires, and what happens on a crash

The lock lives on the job document: { runId, owner: "host:pid", acquiredAt, expiresAt }. It expires on purpose. A lock that never expired would stay stuck forever after a crash.

Normal run

10:01:00

Lock taken, expires 10:03:00

10:01:30

Heartbeat → expires 10:03:30

10:02:00

Heartbeat → expires 10:04:00

10:02:10

Job done, lock cleared

Process crashes

10:01:00

Lock taken, expires 10:03:00

10:01:20

Server restarts. No more heartbeats

10:03:00

Lock expires. Dashboard shows failing: "stopped responding"

next call

Takes the expired lock, marks the old run interrupted, then runs normally

What is stored

The two tracking collections

cron_jobs: one per job

From registry.js (overwritten on every start): jobKey, name, schedules, timezone, enabled, criticality, graceMin, maxDurationMin.

Written by the tracker: lock, lastRun (a short copy of the newest run), lastSuccessAt, consecutiveFailures.

The dashboard reads only this collection for its main table, so it stays fast however much history piles up.

cron_runs: one per call

jobKey, status, scheduledFor, startedAt, finishedAt, durationMs, recordsFetched, recordsProcessed, reason, error, host, pid.

Used for the History panel. Mongo deletes runs older than 90 days by itself.

Run statuses

StatusMeaning
runningStarted, not finished yet.
successFinished and Accord returned rows.
warningFinished, but Accord returned 0 rows. Usually the file is not ready yet.
failedThe job threw an error. The message is saved.
skippedDid nothing: the job is disabled, or it was already running.
interruptedThe process died while this run was going. Found by the next call.
The dashboard

How a job gets its colour

Every 15 seconds the page calls GET /api/health/crons. For each job, status.js checks three things and the worst problem wins.

CheckProblem foundJob becomes
Is it running now?Lock expired: the process diedfailing
Running longer than maxDurationMindelayed
How did the last run end?failed or interruptedfailing
warning (0 rows)delayed
Did the crontab miss a call?A schedule time passed its graceMin with no rundelayed
None of the abovehealthy

The "missed call" check, with numbers

Current NAV runs at 07:31, 10:01, 12:31… with graceMin: 15. At 10:30, the check looks 15 minutes back, to 10:15. The last schedule time before 10:15 is 10:01. Did a run start at or after 09:59 (2 minutes of clock slack)? If not, the job shows "missed run due 16 Nov, 10:01 (crontab did not call it)".

Schedule times from before the job was first synced are never blamed.

Overall is failing if any critical job is failing, delayed if any job is failing or delayed, otherwise healthy. Disabled jobs are not checked.

Start-up

What happens when the API starts

  1. Connect to Mongo

  2. Check registry.js

    Every job needs a key, a handler function and valid cron expressions. One mistake stops the start, so a typo never half-applies.

  3. Create indexes

    Unique jobKey, the 90-day TTL on runs, the 24-hour TTL on staging rows, and the unique keys $merge needs.

  4. Copy job definitions into cron_jobs

    Only the definition fields are touched. The lock, last run and counters stay as they were. A job removed from registry.js is disabled and hidden, not deleted, so its history stays.

  5. Listen on port 4000

    Now the crontab URLs and the dashboard work.

Doing it yourself

Adding a new job

  1. Add its collections

    src/models/accordFeeds.js

    A dump model and a target model with a unique key field.

  2. Write the job

    src/jobs/accordJobs.js

    Usually one defineAccordJob({ ... }) call.

  3. Register it

    src/jobs/registry.js
    {
  jobKey: 'scheme_master',
  name: 'Scheme Master',
  schedules: ['30 23 * * *'],
  criticality: 'normal',
  graceMin: 30,
  maxDurationMin: 5,
  handler: jobs.schemeMaster,
}

  4. Add the crontab line

    Same time as schedules, otherwise the dashboard reports missed calls.

    30 23 * * *  curl -s -H "x-cron-secret: $CRON_SECRET" http://127.0.0.1:4000/api/accord-cron/scheme_master

  5. Restart the API

    The new job appears on the dashboard as "waiting for first run".

Remember: the code never schedules anything. If the crontab line is missing, the job never runs, and the dashboard tells you after the grace period.
